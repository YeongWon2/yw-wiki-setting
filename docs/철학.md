# 두 위키의 철학

**개인 위키는 내가 생각하는 도구이고, 업무 위키는 내 업무 지식을 회사 지식으로 올리는 다리다.** 그래서 정답의 주인, 충돌의 뜻, LLM의 역할이 서로 다르다.

| | 개인 위키 (`personal`) | 개인 업무 위키 (`work`) |
|---|---|---|
| 무엇 | 나를 위한 생각 · 기억 도구 | 내 업무 지식 → 전사 지식으로 가는 중간 단계 |
| 정답의 주인 | 나 (내 말이 가장 높은 근거) | 회사 원천과 전사 위키 (내 위키는 정본이 아님) |
| 충돌의 뜻 | 대부분 "생각이 바뀜" — 오류가 아니라 기록할 변화 | 원천끼리 다름 — 무엇이 맞는지 사람이 정해야 함 |
| LLM의 역할 | 사서: 정리 · 연결 · 찾기. 내 이해와 판단은 내가 쓴다 | 서기: 수집 · 요약 · 결정 기록 · 승격 초안 |
| 실패 모습 | 모으기만 하고 생각하지 않음 · LLM이 대신 이해함 | 한 번 쓰고 안 읽는 위키 · 정본과 어긋남 |

## 개인 위키: 생각하는 도구

1. **노트의 목적은 생각이다.** Matuschak은 노트를 모으는 것이 아니라 잘 생각하는 것이 목표라고 본다. 노트는 기본으로 나를 위해 쓰고, 독자는 따로 정할 때만 둔다. → [Write notes for yourself by default](https://notes.andymatuschak.org/zXDPrYcxUSZbF5M8vM5Y1U9) · [Evergreen notes](https://notes.andymatuschak.org/Evergreen_notes)
2. **모으기는 아는 것이 아니다.** Tietze의 "수집가의 오류": 자료를 모으면 쓸모 있게 느껴지지만, 어떤 것에 대해 아는 것과 그것을 아는 것은 다르다. → [The Collector's Fallacy](https://www.zettelkasten.de/posts/collectors-fallacy) · [Matuschak: Collecting material feels more useful than it usually is](https://notes.andymatuschak.org/zQm6XAB3XXrXLHzF7gahpJ2)
3. **LLM이 이해까지 대신하면 내가 못 쓰게 된다.** 2026년 LLM 위키 비판의 핵심은, 형식 정리는 맡겨도 되지만 이해를 맡기면 위키는 좋아지고 나는 덜 알게 된다는 것이다. 중간 길은 "원본 노트는 내가 쓰고, LLM은 그 주위의 위키를 유지한다"는 것이다. → [LLM Wiki and Germane Load](https://braindetox.kr/en/posts/llm_wiki_cognitive_load_2026.html) · [Robots in the garden (Arango)](https://jarango.com/2026/03/27/robots-in-the-garden/) · [The LLM wiki trend has a retention problem](https://pub.towardsai.net/the-llm-wiki-trend-has-a-retention-problem-nobody-mentions-4b376d288e9c)
4. **연결이 분류보다 먼저다.** Bush의 Memex는 기억처럼 갈라지고 겹치는 연결(trail)로 지식을 엮고, 쓰는 길은 굵어지고 안 쓰는 길은 흐려진다고 봤다. → [Memex](https://en.wikipedia.org/wiki/Memex) · [As We May Think (1945)](https://people.ece.ubc.ca/leei/519/bush-1945.html)
5. **노트 상자는 대화 상대다.** Luhmann은 Zettelkasten을 나를 놀라게 할 수 있는 대화 상대로 봤다. 다만 "제2의 뇌"라는 말은 과장이라는 비판도 많다. 노트는 생각을 대신하지 않고 키운다. → [Revisiting Luhmann's 1981 article](https://danallosso.substack.com/p/revisiting-luhmanns-1981-zettelkasten) · [Zettelkasten Forum](https://forum.zettelkasten.de/discussion/comment/18895)
6. **Karpathy의 원래 용도에 개인이 있다.** 개인(목표 · 건강 · 일지), 연구, 독서가 예시이고, 한 사람이나 작은 팀의 지식 기반으로 설계됐다. → [Karpathy LLM wiki idea file 해설](https://agentpedia.codes/blog/karpathy-llm-wiki-idea-file) · [Implicator 분석](https://implicator.ai/karpathys-llm-wiki-got-16-million-views-the-code-isnt-the-point-2/)

## 업무 위키: 개인 지식을 조직 지식으로

1. **SECI의 표출화 단계다.** Nonaka의 지식 창조 나선에서 개인의 암묵지는 표출화(말로 적기)로 형식지가 되고, 결합(조직 지식으로 합치기)과 내면화(다시 실무로)를 거친다. 업무 위키는 표출화, 전사 위키 승격은 결합, 전사 위키를 읽고 일하는 것은 내면화다. → [SECI, Ba and Leadership (Nonaka 외 2000)](https://verdi.cs.ucl.ac.uk/constructDB/publications/nonaka-seci-2000.html) · [Hitachi 인터뷰](https://www-hitachi-hri-com.itdweb.ext.hitachi.co.jp/english/interview-column/reciprocal/i056.html)
2. **정본은 내 위키가 아니다.** 전사 위키는 조직이 채택한 지식의 유일한 정본이고, 결정이 개인 노트에만 있으면 공유 원천에 먼저 남긴다. → 전사 위키 `SCHEMA.md` 2 · 7절
3. **업무 일지는 성과의 증거다.** 작업 일지와 brag doc은 PR에 안 남는 일(페어링, 리뷰, 회의)까지 남겨 평가 · 이직 때 근거가 된다. 형식은 가볍게. → [Pragmatic Engineer: Work log template](https://blog.pragmaticengineer.com/work-log-template-for-software-engineers/) · [Keep a work journal](https://hawksley.org/2026/01/27/keep-a-work-journal.html) · [The brag doc](https://shipvalue.substack.com/p/the-brag-doc)
4. **결정은 바꾸지 않고 새로 쓴다.** ADR은 채택되면 고정이고, 생각이 바뀌면 새 ADR로 대체한다. 결정 기록의 위험은 "한 번 쓰고 안 읽는" 위키다. → [AWS ADR process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html) · [Fowler: ADR](https://www.martinfowler.com/bliki/ArchitectureDecisionRecord.html) · [Microsoft decision log](https://microsoft.github.io/code-with-engineering-playbook/design/design-reviews/decision-log/)
5. **충돌은 격리하고 사람이 정한다.** 에이전트 기억 연구들은 같은 권위의 다른 출처끼리 다르면 커밋 전에 격리해 사람이 정하게 하고, 기존 기록을 말없이 덮어쓰지 않는다. 자동 수집은 프롬프트 주입 통로이기도 해서, 믿을 수 없는 원천이 검토 없이 위키 페이지가 되면 안 된다. → [MemTX](https://arxiv.org/pdf/2607.23929) · [Memanto](https://arxiv.org/pdf/2604.22085) · [Hyperspell: memory conflict resolution](https://www.hyperspell.com/blog/memory-conflict-resolution) · [ar9av llm-wiki (draft → reviewed)](https://aiagentskills.net/skill/ar9av-obsidian-wiki-llm-wiki) · [nvk/llm-wiki](https://github.com/nvk/llm-wiki)

## 이 세팅에 반영한 것

- **두 위키 공통:** 충돌은 위키에 쓰지 않고 `review/`에서 사람이 정한다(업무 5번). 결정은 superseded로 잇는다(업무 4번). 업데이트는 사람이 말할 때만 한다(개인 2번).
- **개인:** 원본(`raw/daily` · `raw/notes`)은 내가 쓰고 LLM은 고치지 않는다(개인 3번). 내가 말한 결정은 바로 accepted다(정답의 주인은 나).
- **업무:** DEC-ID · `canonical` · `published`로 정본 위치를 적는다(업무 2번). 승격은 drafts → 사람 검토 → PR 순이다(업무 1번). 경력 추출은 업무 일지를 근거로 한다(업무 3번).

## 정한 것 (2026-10-29, v2.1.0에 반영)

1. **개인 위키의 "생각이 바뀜":** 내 생각이 바뀐 것을 충돌(review)로 볼지, Timeline과 superseded 결정으로 바로 기록할지. → 내가 직접 말한 변경은 바로 기록하고, 원천끼리 다를 때만 review로 보낸다.
2. **개인 학습 페이지(강의 개념):** LLM이 이해를 대신 쓰지 않도록 할지. → 개인 위키 concept에 `## My understanding` 칸을 두고 이 칸은 내가 쓴다(LLM은 비워 두고 정리 · 연결만 한다).
3. **개인 위키 고아 페이지:** Memex처럼 안 쓰는 길이 흐려지는 것을 허용할지. → 개인 위키에서는 고아 페이지를 경고만 하고 review로 보내지 않는다.
4. **업무 위키 권위 순서:** 검토할 때 보여 줄 기본 순서. → 전사 위키(채택) > 공유 원천(PR · Jira · Slack) > 내 업무 일지 > Claude 추론. 결정은 여전히 사람이 한다.

자료 확인: 2026-10-29. 대부분 블로그 · 포럼 · 프리프린트라 근거 수준이 고르지 않다. Matuschak · Tietze · Bush · Nonaka · AWS · Fowler는 원문이나 1차 자료다.
